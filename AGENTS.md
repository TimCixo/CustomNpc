# AGENT.md

## Контекст

Этот проект использует scripting API мода CustomNPCs Unofficial для Minecraft 1.21.1.
Основная цель агента — помогать писать, отлаживать и рефакторить скрипты для NPC, диалогов, предметов, компонентов предметов и простого AI/automation поведения.

Среда исполнения:
- Minecraft 1.21.1
- CustomNPCs Unofficial
- Скрипты на JavaScript (Nashorn-style)
- Код пишется внутри Script Tab NPC, Dialog, Timer hooks и похожих мест
- Доступ к внешним файлам мира/сервера часто отсутствует
- Common scripts через отдельные `.js` файлы обычно недоступны
- Поэтому решения должны быть рассчитаны на работу **целиком внутри игрового UI**
- У script hooks в этой среде есть практический лимит размера файла около `65535` байт
- Агент не должен раздувать один hook-файл выше этого лимита; если код подходит к лимиту, нужно выносить логику в другие hooks/скрипты или упрощать реализацию

---

## Главные правила для агента

### 1. Не выдумывай старый API, если он уже не работает
В этой среде многие старые методы из старых версий CustomNPCs либо:
- отсутствуют,
- работают иначе,
- не подходят для Minecraft 1.21.1.

Особенно осторожно относиться к таким вещам:
- `setNbt(...)`
- `setItemNbt(...)`
- `player.executeCommand(...)`
- прямое редактирование item NBT через старые методы

Если метод не подтвержден, не утверждай, что он точно существует.

---

### 2. Предметы в 1.21.1 — это не "старый NBT-мешок"
Начиная с новых версий Minecraft, у предметов важные данные лежат в **data components**, а не только в старом item NBT.

Поэтому:
- не предлагать "просто удалить NBT", если задача касается чарок, custom components, storage UUID и т.д.
- при работе с предметами предпочитать:
  - `item.getMCItemStack()`
  - ванильные Java-классы Minecraft
  - `BuiltInRegistries`
  - `ResourceLocation`
  - `DataComponentType`
  - helper-классы вроде `EnchantmentHelper`

---

### 3. Если задача касается предмета — сначала думать через MCItemStack
Предпочтительный путь работы с предметами:
1. Получить `item = player.getMainhandItem()`
2. Получить `mcStack = item.getMCItemStack()`
3. Работать через ванильный Java API Minecraft / NeoForge-совместимые классы

Примеры:
- снять чарки:
  - `EnchantmentHelper.setEnchantments(mcStack, ItemEnchantments.EMPTY)`
- удалить кастомный компонент:
  - получить `DataComponentType` из `BuiltInRegistries.DATA_COMPONENT_TYPE`
  - вызвать `mcStack.remove(componentType)`
- проверить реальный id предмета:
  - `String(BuiltInRegistries.ITEM.getKey(mcStack.getItem()))`

---

### 4. Не путать display name и registry id
`item.getItemName()` в этой сборке может возвращать отображаемое имя вроде:
- `"Gold Backpack"`

а не реальный id:
- `"sophisticatedbackpacks:gold_backpack"`

Если нужно проверить конкретный предмет, использовать:
```js
var mcStack = item.getMCItemStack();
var itemId = String(BuiltInRegistries.ITEM.getKey(mcStack.getItem()));
````

Не использовать display name для надежной логики, если нужен точный id.

---

### 5. Диалоги CustomNPCs: учитывать ограничения hook-логики

Для dialog hooks помнить:

* `dialogOption(event)` вызывается только у нормального NPC-диалога
* если диалог открыт принудительно через `player.showDialog(...)`, hook может не сработать
* если нужно ловить `dialogOption`, диалог должен быть привязан как обычный dialog NPC

Не предлагать решения, где `dialogOption` гарантированно сработает после `player.showDialog(...)`, если это не подтверждено.

---

### 6. Скрипты по hooks — это не один общий JS-файл

Каждый hook (`init`, `interact`, `timer`, `dialogOption`) воспринимать как отдельную точку входа.

Важно:

* нельзя рассчитывать, что функция из одного hook автоматически доступна в другом
* без common scripts нужно держать reusable-логику внутри одного hook или копировать ее
* передача состояния между hooks — через:

  * `npc.getStoreddata()`
  * `npc.getTempdata()`

---

### 7. StoredData и TempData

Использовать так:

#### StoredData

Для данных, которые должны переживать рестарт:

* режим работы NPC
* координаты привязанного сундука
* флаги включения
* параметры конфигурации

#### TempData

Для временных данных:

* кэш
* промежуточное состояние
* runtime-флаги

Не пытаться передавать через `storeddata` функции или сложные JS-ссылки.

---

### 8. Если нужно переиспользование без доступа к файлам — упрощать архитектуру

Так как часто нет доступа к папке мира/сервера:

* не предлагать common scripts как основной путь, если пользователь не может создавать файлы
* лучше рекомендовать структуру:

  * `init` — минимум
  * `interact` — переключение состояний
  * `timer` — вся основная логика + helper functions

Если пользователь просит "без копипасты", но нет доступа к файлам, предлагать:

* хранить логику в одном основном hook
* между hooks гонять только состояние

---

## Стиль ответов агента

### 1. Писать прикладно

Не расписывать теорию без необходимости.
Сначала:

* что именно сломано,
* почему,
* какой рабочий путь,
* готовый код.

### 2. Давать код целиком, если пользователь явно просит

Если пользователь просит:

* "обнови скрипт"
* "вставь сразу всё"
* "не давай кусками"

то агент обязан отдавать **полный готовый скрипт**, а не набор патчей.

### 3. Не давать "красивые", но бесполезные советы

Не предлагать:

* редактировать файлы мира, если пользователь не имеет доступа
* команды, если на сервере команды урезаны или command blocks выключены
* старые методы API без проверки

### 4. Сначала рабочесть, потом красота

Если есть выбор между:

* более элегантным, но сомнительным решением
* грубым, но точно рабочим

предпочесть рабочее.

## Предпочтительные практики

### Работа с предметами

Предпочитать:

```js
var item = player.getMainhandItem();
var mcStack = item.getMCItemStack();
```

### Работа с реестрами

Предпочитать:

```js
var BuiltInRegistries = Java.type("net.minecraft.core.registries.BuiltInRegistries");
var ResourceLocation = Java.type("net.minecraft.resources.ResourceLocation");
```

### Удаление custom component

Шаблон:

```js
var componentType = BuiltInRegistries.DATA_COMPONENT_TYPE.get(
    ResourceLocation.parse("modid:component_name")
);
mcStack.remove(componentType);
```

### Проверка реального item id

Шаблон:

```js
var itemId = String(BuiltInRegistries.ITEM.getKey(mcStack.getItem()));
```

### Включение / выключение поведения NPC

Через storeddata:

```js
npc.getStoreddata().put("enabled", "1");
```

## Работа с фермером / агро-логикой

Если речь идет о фермере NPC:

* не полагаться полностью на built-in Farmer job
* особенно не полагаться на нее для модовых культур
* при проблемах с поддержкой культур предпочитать scripted automation

### Для scripted farming:

1. искать блоки в радиусе
2. проверять block id / tags / age
3. вести NPC к цели
4. harvest-логика отдельно для разных типов культур
5. складирование в заранее привязанный контейнер

### Для Cobblemon:

Не считать их обычными crops по умолчанию.
Разделять:

* berries
* apricorns

Если у растения свой harvest-flow, не пытаться всегда ломать блок.
Если right-click harvest не удается воспроизвести надежно, использовать детерминированную scripted-логику:

* изменить возраст блока
* напрямую добавить item в cargo / inventory / container

---

## Для Cobblemon berries и apricorns

Считать:

* `#cobblemon:berries`
* `#cobblemon:apricorns`

Отдельно учитывать:

* berries могут иметь свои стадии зрелости
* apricorns могут иметь другие правила сброса стадии

Если пользователь уже установил нужную бизнес-логику, агент должен следовать ей, например:

* berries harvest только на `age >= 5`
* после harvest berries сбрасывать на `age = 3`
* apricorns harvest на `age >= 3`
* после harvest apricorns сбрасывать на `age = 1`

Если scripted ломание блока приводит к потере дропа — не использовать дроп через `destroyBlock` как единственный источник предметов.
Лучше:

* менять state блока напрямую
* добавлять item deterministic-способом в cargo

---

## Чего не делать

* Не обещать, что hook из `showDialog()` точно вызовет `dialogOption`
* Не утверждать, что `getItemName()` всегда возвращает registry id
* Не использовать `storeddata` для ссылок на функции
* Не рекомендовать common scripts как обязательное решение, если пользователь без доступа к файлам
* Не опираться на старый CNPC API без оговорок
* Не говорить "просто удалите NBT", если вопрос касается item components
* Не предлагать `/item replace` или `npc.executeCommand`, если команды на сервере урезаны

---

## Формат помощи по коду

При ответе на запросы пользователя агент должен:

1. Сначала назвать реальную причину проблемы
2. Потом дать рабочий код
3. Потом коротко объяснить, почему это работает
4. Если пользователь раздражен или прямо просит "без кусочков" — отдавать только цельный результат

## Приоритеты

1. Рабочесть на CustomNPCs Unofficial 1.21.1
2. Совместимость с урезанным серверным окружением
3. Работа без файловой системы сервера
4. Минимум копипасты
5. Понятность кода
